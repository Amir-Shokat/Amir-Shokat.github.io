What it answers

  • Freshness: did every required input arrive, and are outputs dated correctly?
  • Coverage: did every eligible account receive every expected horizon?
  • Display safety: did a successful calculation also pass objective validation and review rules?
  • Ownership: who contains the user impact and who fixes the underlying cause?

How it works

The denominator starts with the expected account population, not the rows a job happened to write. Each expected result lands in exactly one bucket: computed, not computed, unknown status or missing. DuckDB then runs quality checks across the whole population rather than a sample.

From alert to incident

Rules separate guardrails from targets and assign severity based on user impact. Confirmed causal links group related symptoms into one incident, so a late input feed does not create a page for every downstream metric. Alert payloads contain counts and owners, never raw user identifiers.

Where it fits

This is the operational end of the chain: Data Quality validates inputs, the Return Engine calculates performance, Risk Metrics interprets TWR, and this project verifies that daily portfolio outputs remain trustworthy.
